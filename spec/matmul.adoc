Matrix multiplication operations take two matrix tiles, matrixA and matrixB, from matrix **tile registers** specified by `ms1` and `ms2`, and accumulate the multiplication result into matrixC specified by `md`, which shall name an **accumulation register**.

`mmacc` updates only the active output tile region of `md` selected by the current `mtilem` and `mtilen` settings. The instruction is accumulative: for each active output element, the new value is computed as the previous accumulator value plus the matrix product contribution. The contents of `md` outside the active output tile region are unspecified after execution.

This specification exposes a single architectural matrix multiply instruction, `mmacc`. The operand and accumulator types are determined by the programmed `mcfg(ms1)`, `mcfg(ms2)`, and `mcfg(md)` state together with the matrix capability description reported by the implementation.

[cols="^2,^3,^3,^3"]
|===
| category   | instructions             | Operand Type            | Accumulator Type
| implementation-defined | mmacc | determined by `mcfg(ms1)` / `mcfg(ms2)` | determined by `mcfg(md)`
|===

If `msaten` equals 1, the output should be saturated for combinations that define saturation behavior. Otherwise, the `mmacc` operation ignores overflow and wraps around the result when wraparound semantics are defined. If the programmed `mcfg` state does not match a supported matrix multiply combination, executing `mmacc` raises an illegal instruction exception.

```
# matrix multiply-accumulate on the active output tile region.
# The three-operand form selects K slice zero.
mmacc   md, ms2, ms1

# Experimental XBitMTE form, with an unsigned 3-bit immediate selector.
mmacc   md, ms2, ms1, kslice
```

Hardware executing unsupported instructions will raise illegal instruction exception.

Executing a matrix multiplication instruction with unsupported `mtilem`, `mtilek`, or `mtilen` settings raises an illegal instruction exception. The programmed tile sizes are illegal when they exceed the architectural limits implied by `ROWNUM`, `TRLEN`, `ARLEN`, and the active operand and accumulator configuration selected by `mcfg`.

[[xbitmte-native-multiply]]
==== Experimental Native Packed B K Slices

The experimental `XBitMTE` contract defines K-slice selection only for signed `int8` or `int4` A, native packed `fp2pack4` or `i1pack8` B, and signed `int32` C. The corresponding capabilities are `i8fp2pack4i32`, `i4fp2pack4i32`, `i8i1pack8i32`, and `i4i1pack8i32`. These type capabilities shall be interpreted together with the experimental `xbitmte` identification described in the programmer's model; they do not imply support by an existing implementation.

For these combinations, let stem:[EW_A] be 8 or 4 bits and stem:[EW_B] be the physical packed width, 2 or 1 bit. Define stem:[Kslot = TRLEN / EW_A] and stem:[Nslices = EW_A / EW_B]. The unsigned `kslice` immediate must satisfy stem:[0 \le kslice < Nslices]. This first experimental version defines full-window computation only: `mtilek` shall equal `Kslot`, stem:[mtilem = ROWNUM], and stem:[mtilen = \min(ROWNUM, ARLEN / 32)]. An out-of-range selector or unsupported tile shape raises an illegal instruction exception. For example, ROWNUM=128, TRLEN=512, and ARLEN=4096 give M=N=128, with K=64 for int8 A or K=128 for int4 A.

For every active output element, the operation is:

[stem]
++++
C[i,j] \leftarrow C[i,j] + \sum_{k=0}^{mtilek-1} A[i,k] \times B[j,kslice \times Kslot + k]
++++

The slice stride is the fixed maximum width-side K capacity `Kslot`. A is consumed starting at K index zero. Separate instructions for successive slices require software to load the corresponding A K blocks and may accumulate into the same C tile. This first version does not define shorter K windows or partial M/N computation for the native packed combinations.

With `TRLEN=512` bits, the windows are:

[cols="^4,^2,^2,^2,^3"]
|===
| Capability | Compute K (`Kslot`) | Resident B elements per row | `Nslices` | Legal `kslice`
| `i8fp2pack4i32` | 64 | 256 | 4 | 0-3
| `i4fp2pack4i32` | 128 | 256 | 2 | 0-1
| `i8i1pack8i32` | 64 | 512 | 8 | 0-7
| `i4i1pack8i32` | 128 | 512 | 4 | 0-3
|===

For all other operand combinations, the selector shall be zero, and a nonzero selector raises an illegal instruction exception. The three-operand assembly form is always an alias for `kslice=0`. These rules do not define slicing for a narrow A operand or for `fp2pack5`.

The maximum register capacities describe storage limits, not additional supported tile shapes. In particular, neither shorter K computation nor partial M/N computation shall be inferred from a type capability string in this first experimental version.

For native packed `mmacc`, `ms1` names A, `ms2` names B, and `md` names C. A and B shall be distinct tile registers (`tr0`-`tr3`), and C shall be an accumulation register (`acc0`-`acc3`). Unsupported register classes, A/B aliasing, an unsupported type triple, or an unsupported full-window shape raises an illegal instruction exception before updating C. Packed A or C, unsigned A, and types other than the four combinations above are not native packed multiply combinations. These new checks do not add an A/B-alias exception or change validation of existing ordinary operations.

The selector is not reduced modulo `Nslices`. An assembler accepts a constant selector in 0..7; the smaller range for a particular type combination is checked when the instruction executes. With `xbitmte` unavailable, any nonzero selector is illegal. Selector zero does not identify a different data representation: a packed B type always has the native representation defined in <<xbitmte-native-types>>. The canonical assembly spelling for selector zero is the three-operand form; an explicit fourth operand of zero has identical encoding.

The instruction uses its associated operand configurations, tile sizes, and arithmetic control state; subsequent configuration writes do not reinterpret an earlier multiplication. The new type, shape, and selector rules do not change existing matrix privilege, memory-fault, or exception-priority rules. A consumed ternary data code `10` has undefined numerical behavior rather than requiring an illegal instruction exception; it does not make an otherwise illegal control combination legal.

With `msaten=0`, every native output is accumulated modulo stem:[2^{32}]. Each product uses the mathematical signed A value and the decoded ternary or binary B value before the i32 wrap; in particular, stem:[(-128) \times (-1) = 128] and stem:[(-8) \times (-1) = 8]. These experimental combinations do not establish a common overflow result for `msaten=1`; that result is implementation-defined. Neither value of `msaten` is an illegal control condition by itself. Native packed multiplication does not automatically update `msat`.
