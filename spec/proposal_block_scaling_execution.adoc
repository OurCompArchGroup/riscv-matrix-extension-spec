=== 执行模型与编码方向

==== 为什么不能直接把所有类型都塞进 matmul 编码

如果把下面几类信息全部平铺进单条 matmul 的类型字段：

* A 的量化类型
* B 的量化类型
* 是否启用 block scaling
* block size
* scale 类型（`UE8M0` / `UE4M3` / future）
* 输出/累加类型

那么当前矩阵乘法编码空间会很快不够用。尤其是一旦同时覆盖：

* unscaled FP8
* MXFP8
* MXFP4
* NVFP4
* A/B 异构低精度组合

单靠一个扩大的 `s_type` 表并不经济，也不利于长期扩展。

==== 推荐编码方向

本提案建议把“执行模型”和“最终字段编码表”拆开处理。

第一阶段只冻结下面三件事：

* matmul **可以**进入 scaled 模式。
* scaled 模式从与 `tr*` 配对的 `sa*` / `sb*` 读取 scale。
* A/B 操作数可以是异构低精度类型，但**不在本阶段冻结完整的编码枚举表**。

换句话说，本提案当前更强调：

* 先固定 **执行模型**
* 再逐步收敛 **编码细节**

而不是一次性把所有类型、缩放格式和混合组合编码成一张大表。

==== 建议保留的最小编码概念

如果未来继续推进该方向，matmul 编码至少应保留三类概念：

* **基础源类型**：例如 `e4m3`、`e5m2`、`fp16` 等
* **A/B 是否异构**：例如一个 `ab_diff` 或等价机制
* **是否读取 scale 寄存器**：一个 scaled-mode 选择位或 opcode 族区分

而 `block_size` 与 `scale_type` 则优先由 **scale 格式本身** 决定，不再重复编码进每个数据类型枚举值。

这比“给 `mxfp8_e4m3`、`mxfp8_e5m2`、`nvfp4`、`mxfp4` 分别占用独立 `s_type` 编码”更可扩展。

==== Scale Load 指令方向

如果采用 scale 寄存器方案，则仍然需要专门的软件可见装载路径把 scale 数据写入 `sa*` / `sb*`。

因此，保留以下方向是合理的：

* `mlascale*`：把 A-side scale 装入 `sa*`
* `mlbscale*`：把 B-side scale 装入 `sb*`

这与 NVIDIA/AMD 的“scale 由 matmul 消费”是一致的；不同点只是本提案把 scale 先落入架构寄存器，而不是直接作为单条 matmul 的显式附加操作数。

==== 第一阶段建议的数学语义

为了避免 NVIDIA/AMD 两种语义在 `UE4M3` 场景下的分歧，第一阶段建议只冻结：

* `UE8M0`
* `block_size = 32`

在这个限定下，scale 是纯 2 的幂次偏移。无论硬件选择：

* 先 scale 再乘，还是
* 先做 block dot-product 再统一乘上 scale

最终架构结果都可以要求保持一致。

因此，第一阶段建议把架构语义写成：

----
D[i][j] += sum_k ((A[i][k] * scale_A[i][k / 32]) *
                  (B[k][j] * scale_B[k / 32][j]))
----

并允许实现以任何与之**严格等价**的内部数据流完成计算。

==== 第一阶段执行与数据流

MXFP8/MXFP4 使用相同的 block-scale 关联关系：

* A tile 的 scale 行对应 `tr[ms1]` 的逻辑 M 行。
* B tile 的 scale 行对应 `tr[ms2]` 的逻辑 N 行，即 `B^T` 寄存器行。
* 每个 block 覆盖 32 个 K 元素，scale 为 E8M0。
* E8M0=255 表示 NaN scale；任何用户 block 的 scale 为 255 时，对应输出
  按 IEEE NaN 传播，不允许静默截断成有限指数。
* 未使用的 tail block 不访问 scale；其数据按零处理。

实现可以把 scale 提前叠加到元素指数，也可以先计算 block dot-product 再
应用 scale；两种实现必须符合同一独立浮点 golden。归约、异常传播和最终
FP32 舍入必须与标准 MX 元素解码一致。

第一阶段实验实现冻结以下可观测数值契约：

* 每个 `A[i][k]` 和 `B[k][j]` 先按对应 E8M0 scale 精确缩放。E8M0
  只改变二进制指数，不改变元素的符号、尾数或零。
* product 以至少足够的内部范围保留，再参与 FP32 累加；实现不得因为先计算
  仅一侧的缩放乘积而产生架构可见的中间溢出。例如有限元素与 E8M0 的组合，
  即使一侧中间值大于 FP32 最大有限值，只要最终一个 block 的 contribution
  可表示，就不能仅因实现顺序不同而产生 Inf。
* 每个 block 的 exact contribution 为
  `sum_{k in block} exact(A_scaled * B_scaled)`。不同 block 的 contribution
  按 K 递增顺序加入 C。
* 每次加入 block contribution 后，按当前 `mfrm` 舍入到 FP32。第一阶段软件、
  golden 和 RTL bring-up 固定使用 RNE；其他合法 `mfrm` 必须按
  `program_model.adoc` 的定义实现后才可报告为支持。
* FP32 累加遵循 IEEE 754 binary32 的 subnormal、overflow、NaN 和 signed-zero
  规则；`mfflags` 反映架构可见的 FP32 操作异常。实现内部的精确乘积或归约树
  不得静默改变最终的 NaN/Inf/zero 分类。
* A 或 B 用户 block 的 E8M0 为 255 时，该 block 的 contribution 为 NaN，
  并按 IEEE NaN 传播到输出；不得把 255 当作有限指数。

该定义允许并行归约，但并行实现的每一部分必须满足与上述顺序 golden
逐位等价，或明确由 capability 报告不同的舍入契约。仅做到“数学上近似相等”
不满足本阶段要求。

scale valid 和对应 tile register 的关联是执行的一部分，不是性能优化。
硬件不得在 scale 缺失时消费 A/B/C 向量后再等待一个永远不会完成的输出；
数据、scale 和 FPE 接受应形成单个逻辑 token。实现可以使用原子 join、
预取 hold register 或事务式回滚，但架构可见结果必须等价于“先验证全部
输入，再执行”。

==== 暂缓冻结的内容

以下内容建议明确标记为 deferred，而不是在第一阶段写死：

* `UE4M3` scale
* `NVFP4`
* `FP6`
* 所有 4-bit load 的精确编码表
* 完整 `s_type` 枚举表
* 除 RNE 外的 MX `mfrm` 模式

这些内容一旦提前冻结，会把编码、精度语义和软件模型三件事耦合在一起。

==== Discovery 方向

block scaling 路线不应通过新的 `misa` 位发现。更合理的方向是：

* 扩展名仍然通过 `riscv,isa-extensions`
* 具体矩阵能力通过 `riscv,matrix-isa-caps`

也就是说，如果未来存在“支持 block scaling 的 MXFP8 matmul”，应设计新的 capability 表示方式，而不是回退到 `misa` 能力位。
