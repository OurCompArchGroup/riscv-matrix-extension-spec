== 方案 B：扁平化编码（func4 直接编码源类型）

[WARNING]
====
**待讨论** — 本文档为矩阵乘法指令编码重构的候选方案 B，尚未定稿。
====

=== 设计思路

将 func4 直接用作源操作数类型编码（s_type），目标类型用原 ctrl 位置的 3 bits 编码（d_type）。原 s_size 和 d_size 不再需要，变为 reserved 位，可供未来扩展。

=== 指令格式

[wavedrom, ,svg]
....
{reg: [
  {bits: 7,  name: 'opcode', attr: '0101011', type: 8},
  {bits: 3,  name: 'md/ms3', type: 2},
  {bits: 2,  name: 'reserved', type: 8},
  {bits: 3,  name: 'func3', attr: '000', type: 8},
  {bits: 3,  name: 'ms1', type: 3},
  {bits: 2,  name: 'reserved', type: 8},
  {bits: 3,  name: 'ms2', type: 4},
  {bits: 3,  name: 'd_type[2:0]', type: 7},
  {bits: 2,  name: 'uop', attr: '10', type: 8},
  {bits: 4,  name: 's_type[3:0]', type: 4},
], config: {lanes: 1, hspace: 1000}}
....

变更说明：

* func4 位置（inst[31:28]）→ s_type[3:0]，直接编码源操作数类型
* ctrl 位置（inst[25:23]）→ d_type[2:0]，直接编码目标操作数类型
* 原 s_size（inst[19:18]）→ reserved（类型信息已在 s_type 中）
* 原 d_size（inst[11:10]）→ reserved（类型信息已在 d_type 中）
* 释放 4 bits reserved，可用于未来扩展（如混合符号、转置模式等）

=== Reserved 位的潜在用途

方案 B 释放了 4 bits reserved（原 s_size[1:0] + d_size[1:0]），可用于：

* *混合符号*：1 bit 标识 A、B 操作数是否使用不同符号（如 int8_signed × int8_unsigned）
* *转置模式*：1 bit 标识 B 矩阵是否转置
* *饱和模式*：覆盖 mcsr.msaten 的局部控制
* *未来类型扩展*：当 s_type 的 11 个值不够时，reserved 位可扩展 s_type 到 5-6 bits

=== 优缺点

*优点：*

* 编码最简洁：s_type 和 d_type 各占连续位域，解码只需读两个字段即可确定完整类型
* 不依赖 func4 的语义，uop=10 下所有指令统一用 s_type+d_type 描述
* 释放 4 bits reserved，为未来扩展留出空间
* 硬件可直接用 s_type 高位判断整数/浮点（0000-0011=整数，0100+=浮点）

*缺点：*

* func4 位置不再是"操作类型"，而是"源数据类型"，与其他 uop 类别（config/load-store/misc）中 func4 的语义不一致
* 无法通过 func4 单独区分整数和浮点执行路径，需要解码 s_type

=== 方案 A 与方案 B 对比

[cols="^3,^5,^5"]
|===
| | *方案 A（层次化）* | *方案 B（扁平化）*

| func4 含义
| 操作族（整数/浮点），与其他 uop 一致
| 源类型，仅 uop=10 下语义不同

| 类型字段
| s_type(4) + d_type(3)，d_type 跨两个位域
| s_type(4) + d_type(3)，均为连续位域

| Reserved 位
| 无额外 reserved
| 4 bits reserved（原 s_size + d_size）

| 解码复杂度
| 先解 func4 路由，再解 s_type/d_type
| 直接解 s_type + d_type

| 扩展性
| func4 可增加新操作族（如 conversion）
| reserved 位可扩展类型或增加修饰符

| 与原 spec 兼容性
| func4 语义兼容
| func4 语义变更
|===
