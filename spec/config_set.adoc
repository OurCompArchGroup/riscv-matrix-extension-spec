Due to hardware resource constraints, one of the common ways to handle large-sized matrix multiplication is "tiling", where each iteration of the loop processes a subset of elements, and then continues to iterate until all elements are processed. The Matrix extension provides direct, portable support for this approach.

The block processing of matrix multiplication requires three levels of loops to iterate in the direction of m/k/n of the input application tiles.

For each iteration, most of the matrix multiplication can fully use the input tile registers. But when dealing with the tail of each input application tile's dimension, the length of each multiplication dimension like mtilem/mtiln/mtilek need to be updated to proper tail size.

Tail handling requires the corresponding operation and tile shape to be supported. The first experimental `XBitMTE` native packed combinations define full M/N tiles and full K windows only; programming a smaller tile does not enable tail computation for those combinations. Their packed B load transfers a full physical row regardless of `mtilek`.

A set of instructions is provided to allow rapid configuration of the values in mtile* to match application needs.


The msettile{m|k|n}[i] instructions set the mtilem/mtilek/mtilen CSRs based on their arguments.

The immediate forms encode a 10-bit unsigned operand; the GPR forms use the XLEN-bit source value. The native packed shape checks in <<xbitmte-native-multiply>> use the complete configured tile values, not just low bits that happen to match a supported shape. This extension does not add shape checks to existing ordinary operations.

```
msettilemi imm  # imm = new mtilem
msettilem  rs1  # rs1 = new mtilem
msettileki imm  # imm = new mtilek
msettilek  rs1  # rs1 = new mtilek
msettileni imm  # imm = new mtilen
msettilen  rs1  # rs1 = new mtilen
```

The `msetcfg` instruction programs the `mcfg` architectural registers associated with `tr0`-`tr3` and `acc0`-`acc3`. The companion `mgetcfg` instruction reads the selected `mcfg` value back into a GPR. `msetcfg` is the only instruction that modifies `mcfg` state.

The `mcfg` target selector reuses the same 3-bit numbering as `tr0`-`acc3`:

```
000 -> mcfg0 (for tr0)
001 -> mcfg1 (for tr1)
010 -> mcfg2 (for tr2)
011 -> mcfg3 (for tr3)
100 -> mcfg4 (for acc0)
101 -> mcfg5 (for acc1)
110 -> mcfg6 (for acc2)
111 -> mcfg7 (for acc3)
```

`mcfg_d1` is the destination selector and chooses which `mcfg` register is updated.

For `msetcfg`, `inst[19:15]` holds `rs1`, `inst[11:7]` holds `mcfg_d1`, `inst[24:20]` is reserved zero, and the selected `mcfg` register is assigned the raw XLEN-bit value of `x[rs1]`. Bits `x[rs1][3:0]` provide `type_code`, and bits `x[rs1][7:4]` provide `table_sel`. Bits `x[rs1][XLEN-1:8]` are stored unchanged and do not affect hardware behavior.

For `mgetcfg`, `inst[19:15]` holds `mcfg_s1`, `inst[11:7]` holds `rd`, `inst[24:20]` is reserved zero, and the selected `mcfg` value is copied to `x[rd]` without modification. Bits `x[rd][3:0]` return `type_code`, bits `x[rd][7:4]` return `table_sel`, and bits `x[rd][XLEN-1:8]` return the stored uninterpreted payload.

```
msetcfg  mcfg0, rs1     # config state for tr0  = x[rs1]
msetcfg  mcfg1, rs2     # config state for tr1  = x[rs2]
msetcfg  mcfg5, rs1     # config state for acc1 = x[rs1]
mgetcfg  rd, mcfg0      # rd = mcfg0
mgetcfg  t0, mcfg5      # t0 = mcfg5
```

The selected `table_sel` / `type_code` combination must be one of the defined `mcfg` encodings described in the programmer's model. Unsupported configurations cause an illegal instruction exception.

The native type encodings in <<xbitmte-native-types>> use `table_sel=0`, with type code 13 for `fp2pack4` and 15 for `i1pack8`. Under this native contract, both require `xbitmte`; when it is not enabled, configuring either type raises an illegal instruction exception before changing `mcfg`. The existing handling of other configurations and uninterpreted high bits is unchanged.
