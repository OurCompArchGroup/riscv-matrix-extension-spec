== Programmer's Model

The matrix extension introduces the following architectural state:

* **Matrix Registers**: Eight two-dimensional matrix registers, divided into 4 tile registers (tr0-tr3) and 4 accumulation registers (acc0-acc3). Tile registers store input matrices A and B, with size determined by TLEN (total bits) and TRLEN (bits per row). Accumulation registers store output matrix C, with size determined by ALEN and ARLEN. Both register types share the same row count (stem:[ROWNUM = TLEN/TRLEN]).

* **Matrix Configuration Registers**: Eight addressable architectural registers, `mcfg0`-`mcfg7`, that record the programmed configuration of `tr0`-`tr3` and `acc0`-`acc3`. These are architectural registers, not CSRs. They are updated by `msetcfg` and may be read back through `mgetcfg`. The target selection encoding for `mcfg0`-`mcfg7` reuses the same 3-bit numbering as `tr0`-`acc3`.

* **CSRs (Control and Status Registers)**: Seven CSRs that control matrix operations, including tile dimension configuration, arithmetic mode control, and hardware capability reporting.

* **Modified Standard CSRs**: The matrix extension modifies one standard RISC-V CSR: `mstatus`/`sstatus` adds a 2-bit MS field for matrix context status tracking (analogous to VS for vector). The Zames extension is not indicated in the `misa` Extensions field; it is reported via device tree.

=== Matrix Configuration Registers

The `mcfg` architectural registers hold the programmed matrix configuration for each matrix register. `mcfg0`-`mcfg3` correspond to `tr0`-`tr3`, and `mcfg4`-`mcfg7` correspond to `acc0`-`acc3`.

The 3-bit `mcfg` selector encoding is shared with the matrix-register numbering:

[cols="^2,^3,^3"]
|===
| Selector | Matrix Register | Configuration Register
| 000 | tr0 | mcfg0
| 001 | tr1 | mcfg1
| 010 | tr2 | mcfg2
| 011 | tr3 | mcfg3
| 100 | acc0 | mcfg4
| 101 | acc1 | mcfg5
| 110 | acc2 | mcfg6
| 111 | acc3 | mcfg7
|===

Only the `msetcfg` instruction updates `mcfg` state. The `mgetcfg` instruction reads a selected `mcfg` register and writes its zero-extended value to a GPR. Matrix load/store, matrix multiplication, and misc instructions validate their required operand configuration against the programmed `mcfg` state and do not implicitly rewrite it.

Each `mcfg` register uses the least-significant four bits to hold `type_code[3:0]`, and bits `mcfg[7:4]` hold `table_sel[3:0]`. The upper bits are reserved and shall be written as zero.

.mcfg register layout (illustrated for RV32)
[wavedrom, ,svg]
....
{reg: [
  {bits: 4,  name: 'type_code', attr: '[3:0]', type: 5},
  {bits: 4,  name: 'table_sel', attr: '[7:4]', type: 6},
  {bits: 24, name: '0', attr: '[31:8]', type: 8}
], config: {lanes: 1, hspace: 1000}}
....

For RV64, the same rule applies: bits `mcfg[3:0]` hold `type_code`, bits `mcfg[7:4]` hold `table_sel`, and bits `mcfg[XLEN-1:8]` are reserved zero.

When software executes `mgetcfg`, the selected `mcfg` value is returned in XLEN form with bits `[7:4] = table_sel`, bits `[3:0] = type_code`, and all upper bits zero.

Encoding table `table_sel = 0` is defined below. Other encoding tables are selected by non-zero `table_sel` values and may assign different meanings to the same `type_code`.

[cols="^2,^5"]
|===
| `type_code[3:0]` in table 0 | Meaning
| 0000 | `int4`
| 0001 | `uint4`
| 0010 | `int8`
| 0011 | `uint8`
| 0100 | `int32`
| 0101 | `nvfp4`
| 0110 | `mxfp4`
| 0111 | `fp8e5m2`
| 1000 | `fp8e4m3`
| 1001 | `mxfp8`
| 1010 | `fp16`
| 1011 | `bf16`
| 1100 | `tf32`
| 1101 | `fp32`
| 1110 | `fp2pack4`
| 1111 | `fp2pack5`
|===

When software programs an `mcfg` register, selecting a configuration that is not supported by the implementation raises an illegal instruction exception immediately at the `msetcfg` operation. The set of supported matrix operation capabilities is reported through the matrix capability description in the device tree, using the naming rules defined by the relevant instruction chapters.

=== CSR Registers

==== Matrix ISA Capabilities (Device Tree)

Matrix ISA capabilities are reported via the device tree rather than through a dedicated CSR. The `/cpus/cpu@X` node in the device tree includes a `riscv,matrix-isa-caps` property that lists the supported matrix operation capabilities.

For matrix multiply capabilities, the capability string uses the format `<input_type_a><input_type_b><output_type_c>`. This specification does not enumerate every legal capability string in one global table. Instead, it defines the naming rules for each type token, and the relevant instruction chapters define which combinations are legal.

Integer type tokens use `i<width>` for signed integer types and `u<width>` for unsigned integer types, for example `i8`, `u8`, `i32`, or `u32`.

Floating-point type tokens use direct names. Supported token forms include `nvfp4`, `mxfp4`, `mxfp8`, `fp8`, `fp8e4m3`, `fp8e5m2`, `fp16`, `bf16`, `fp32`, `fp64`, and `tf32`.

For conversion capabilities, the capability string uses the format `<input_type><output_type>cvt`. Relevant instruction chapters define whether a given conversion capability covers one direction or both directions between the named types.

Element-wise support may be advertised with standalone capability strings. `iew` indicates support for integer element-wise operations, and `few` indicates support for floating-point element-wise operations.

.Device Tree Example
[source,dts]
----
cpus {
    cpu@0 {
        compatible = "riscv";
        riscv,isa = "rv64imafdcv";
        riscv,isa-extensions = "zames";
        riscv,matrix-isa-caps = "i8i8i32", "bf16bf16fp32", "fp8e4m3fp8e4m3fp32", "iew", "few";
    };
};
----

==== Matrix Tile Size Registers, mtilem/mtilek/mtilen

The XLEN-bit-wide read-only `mtilem/mtilek/mtilen` CSRs can only be updated by the `msettile{m|k|n}{i}` instructions. The registers holds 3 unsigned integers specifying the tile shapes for tiled matrix.

==== Matrix Control and Status Register, mcsr

The `mcsr` CSR is a WARL read-write register. Bits[XLEN-1:12] are reserved and should be written with zero. 
The `mcsr` register has 5 fields. The mxrm, msat, mfflags, mfrm, msaten separate CSRs can also be accessed via fields in the matrix control and status CSR, mcsr.

.`mcsr` register layout
[cols="^2,^2,8"]
|===
|     Bits | Name       | Description
| XLEN-1:12| 0          | Reserved if non-zero.
|       11 | msaten    | integer and fp8 saturation mode.
|     10:8 | mfrm      | Float-point arithmetic instruction rounding mode.
|      7:3 | mfflags	| Float-point arithmetic instruction accrued exception flags
|        2 | msat      | Fixed-point arithmetic instruction accrued saturation flag.
|      1:0 | mxrm      | Fixed-point arithmetic instruction rounding mode.
|===

=== mcsr Sub-field CSRs

==== Matrix Fixed-Point Rounding Mode, mxrm

`mxrm` field indicates the rounding mode of fixed-point instructions. Suppose the pre-rounding result is v, and d bits of that result are to be rounded off. Then the rounded result is `(v >> d) + r`, where r depends on the rounding mode as specified in the following table.

[cols="^2,^4,^9,7"]
|===
|  mrm  |  Mnemonic  |  meaning                                      |  Rounding Increment r

|  00   |  RNU       |  round-to-nearest-up (add +0.5 LSB)           |  `v[d-1]`
|  01   |  RNE       |  round-to-nearest-even                        |  `v[d-1] & (v[d-2:0]!=0 \| v[d])`
|  10   |  RDN       |  round-down (truncate)                        |  0
|  11   |  ROD       |  round-to-odd (OR bits into LSB)              |  `!v[d] & v[d-1:0]!=0`
|===

The rounding functions are used to represent this operation in the instruction descriptions below:

```
roundoff_unsigned(v, d) = (unsigned(v) >> d) + r
roundoff_signed(v, d)   = (signed(v) >> d) + r
```

==== Matrix Fixed-Point Saturation Flag, msat

The matrix fixed-point saturation flag `msat` holds a single read-write least-significant bit(`msat[0]`) that indicates if a fixed-point instruction has had to saturate an output value to fit into a destination format. The upper bits, `msat[XLEN-1:1]`, should be written as zeros.
The matrix fixed-point saturation flag(msat)  is given a separate CSR address to allow independent access, but is also reflected as a field in mcsr.

==== Matrix Float-Point Exception Flags, mfflags
The matrix float-point exception flags(`mfflags`) holds a five-bit read-write fields in the least-significant bits(`mfflags[4:0]`). The upper bits, `mfflags[XLEN-1:5]`, should be written as zeros.
The matrix float-point exception flags(mfflags)  is given a separate CSR address to allow independent access, but is also reflected as a field in mcsr.
The float matrix multiplication and float pointwise instructions update accrued exception fflags in mfflags.
[cols="^2,^5"]
|===
|  bits     |  Meaning      

|  0        |  NX
|  1        |  UF
|  2        |  OF
|  3        |  reserved for future use
|  4        |  NV
|===

==== Matrix Float-Point Rounding Mode, mfrm

The matrix float-point rounding mode `mfrm` holds a three-bit read-write fiels in the least-significant bits(`mfrm[2:0]`). The upper bits, `mfrm[XLEN-1:3]`, should be written as zeros.
The matrix float-point rounding mode `mfrm` is given a separate CSR address to allow independent access, but is also reflected as a field in mcsr.

[cols="^1,^1,<4"]
|===
| *mfrm* | *Mnemonic* | *Meaning*
|  000  |  RNE       | Round to Nearest, ties to Even
|  001  |  RTZ       | Round towards Zero
|  010  |  RDN       | Round Down (towards stem:[-\infty])
|  011  |  RUP       | Round Up (towards stem:[+\infty])
|  100  |  RMM       | Round to Nearest, ties to Max Magnitude
|  101  |            | Invalid
|  110  |            | Invalid
|  111  |            | Invalid
|===

If `mfrm` is set to an invalid value (101-111), any subsequent attempt to execute a floating-point operation with a dynamic rounding mode will cause an illegal instruction exception. 

==== Matrix Saturation Mode Enable, msaten
The matrix saturation mode `msaten` holds a single read-write least-significant bit(`msaten[0]`) that defines the saturation mode when the operation result is fp8 or integer. The upper bits, `msaten[XLEN-1:1]`, should be written as zeros.
The matrix saturation mode(msaten)  is given a separate CSR address to allow independent access, but is also reflected as a field in mcsr.

[cols="^2,^5"]
|===
|  msaten   |  Meaning      

|  0        |  non-saturation mode
|  1        |  saturation mode
|===

Conversion from all other values first applies rounding to reduce the mantissa bit count to that of the destination FP8 format. After that, if the rounded magnitude is above the maximum destination magnitude: 

    if `msaten` = 1: 
        fp8 conversions: generate the max normal FP8 magnitude 
        mmacc operations: the result should be saturated
        integer arithmetic operations: the result should be saturated
    if `msaten` = 0:  
        fp8 conversion:E4M3 destination: generate a NaN 
                       E5M2 destination: generate an infinity
        mmacc operations: ignore the overflow and wrap around the result       
        integer arithmetic operations: ignore the overflow and wrap around the result       


=== Matrix Context Status in mstatus and sstatus

A 2-bit matrix context status field, MS, should be added to mstatus and shadowed in sstatus. It is defined analogously to the vector context status field, VS.

The MS field is located at bits [26:25] in both mstatus and sstatus registers.

.MS field values
[cols="^1,1"]
|===
| *ms[1:0]* | *Meaning*
|  00       | All Off
|  01       | Initial
|  10       | Clean
|  11       | Dirty
|=== 

Attempts to execute any matrix instructions, or to access the matrix CSRs raise an illegal instruction exception when MS is set to off. If MS is set to initial or clean, executing any instructions that change the matrix state will change the ms to dirty. 

An implementation can use the activity of the Initial state to influence the choice of power-saving states.

=== Standard RISC-V ISA Extensions (misa CSR)

The misa CSR is a WARL read-write register reporting the ISA supported by the hart. The Extensions field encodes the presence of standard extensions, with a single bit per letter of the alphabet.

.misa register layout (RV64)
[wavedrom, ,svg]
....
{reg: [
  {bits: 26, name: 'Extensions[25:0] (WARL)', type: 4},
  {bits: 36, name: 'WLRL', type: 8},
  {bits: 2,  name: 'MXL', type: 5}
], config: {lanes: 2, hspace: 1024}}
....

.Standard ISA Extension Encoding in misa.Extensions
[cols="^1,^1,8"]
|===
| *Bit* | *Character* | *Description*
| 0  | A | Atomic extension
| 1  | B | B extension
| 2  | C | Compressed extension
| 3  | D | Double-precision floating-point extension
| 4  | E | RV32E/64E base ISA
| 5  | F | Single-precision floating-point extension
| 6  | G | Reserved
| 7  | H | Hypervisor extension
| 8  | I | RV32I/64I base ISA
| 9  | J | Reserved
| 10 | K | Reserved
| 11 | L | Reserved
| 12 | M | Integer Multiply/Divide extension
| 13 | N | Tentatively reserved for User-Level Interrupts extension
| 14 | O | Reserved
| 15 | P | Tentatively reserved for Packed-SIMD extension
| 16 | Q | Quad-precision floating-point extension
| 17 | R | Reserved
| 18 | S | Supervisor mode implemented
| 19 | T | Reserved
| 20 | U | User mode implemented
| 21 | V | Vector extension
| 22 | W | Reserved
| 23 | X | Non-standard extensions present
| 24 | Y | Reserved
| 25 | Z | Reserved
|===

The **Zames** (Attached Matrix Extension Simplified) is a multi-letter extension and is not represented as a single bit in the misa.Extensions field. Multi-letter extensions like Zames are reported through the device tree `riscv,isa-extensions` property in the `/cpus/cpu@X` node as a list of lowercase extension name strings. Software can discover the presence of Zames by checking for the string `"zames"` in this list.
