=== 基于 Scale 寄存器的架构状态提案

==== 设计动机

NVIDIA 和 AMD 的公开 ISA 都更接近“每条 matmul 显式接收 scale 输入”的模式。但对本仓库的 32-bit 指令编码约束而言，若同时保留：

* A/B 操作数寄存器编号
* 输出寄存器编号
* A/B 类型选择
* 混合类型支持
* scale 类型与 block scaling 模式

则单条矩阵乘法指令的编码压力会迅速失控。因此，这里提出一个 **RISC-V 化的 scale 寄存器方案**：把 scale 作为可见架构状态，而不是每条指令的显式附加操作数。

==== 新增架构状态

在现有 `tr0-tr3`、`acc0-acc3` 之外，新增 8 个 scale 寄存器：

[cols="^2,^2,^7",options="header"]
|===
| Category | Name | Description
| A-side scale | sa0-sa3 | A 操作数对应的 scale 寄存器组
| B-side scale | sb0-sb3 | B 操作数对应的 scale 寄存器组
|===

这里的 `sa*` / `sb*` 只是逻辑命名。它们是否占用统一的矩阵寄存器编号空间，还是在编码上使用独立寄存器类，留待后续编码提案收敛时再冻结。

语义上的关联关系固定为：

* `sa[i]` 与 `tr[i]` 配对，表示 A 操作数的 scale。
* `sb[i]` 与 `tr[i]` 配对，表示 B 操作数的 scale。

这样的固定配对牺牲了一部分灵活性，但避免了在 matmul 编码中额外加入两个 scale 寄存器字段。

==== Scale 寄存器容量

对某一类 block scaling 格式，定义：

* `block_size(fmt)`：该格式的块大小，例如 MX 路线为 32。
* `scale_bits(fmt)`：scale 在寄存器中的存储位宽，例如 `UE8M0` 为 8。

则单个 scale 寄存器每行位宽为：

----
SRLEN(fmt) = (TRLEN / block_size(fmt)) * scale_bits(fmt)
----

单个 scale 寄存器总位宽为：

----
SLEN(fmt) = ROWNUM * SRLEN(fmt)
----

对第一阶段建议范围 `UE8M0 + block_size=32`：

----
SRLEN = TRLEN / 4
SLEN  = TLEN / 4
----

这意味着 scale 寄存器的物理容量明显小于 tile 寄存器，适合实现为独立寄存器文件，或实现为 tile 文件旁边的缩比寄存器区。

==== 逻辑形状

为了和当前 `C = A x B^T` 的 tile 存储方式对齐，scale 寄存器的**逻辑形状**应和操作数在 tile 寄存器中的方向一致，而不是和未转置的原始矩阵概念强行对齐：

* `sa[i]` 的活动形状：`mtilem x ceil(mtilek / block_size)`
* `sb[i]` 的活动形状：`mtilen x ceil(mtilek / block_size)`

其中：

* `sa[i]` 的行对应 A tile 的 `M` 维。
* `sb[i]` 的行对应 B tile 在寄存器中的 `N` 维，因为当前右操作数以 `B^T` 形式参与计算。

从源矩阵的数学视角看，B-side scale 仍可理解为 `(mtilek / block_size) x mtilen`；这里采用 `mtilen x ceil(mtilek / block_size)` 只是为了和当前 `B^T` 寄存器布局保持一致，便于描述寄存器内活动形状和逐行加载约定。

==== 上下文与 MS 状态

如果实现 block scaling 能力，则 scale 寄存器属于 **matrix context** 的一部分：

* 对 `sa*` / `sb*` 的写入会使 `MS` 从 Initial/Clean 进入 Dirty。
* 执行使用 scale 的 matmul 会读取 scale 寄存器，因此 scale 寄存器必须参与上下文切换语义。
* OS 或运行时在保存/恢复 matrix context 时，不能只考虑 `tr*` 和 `acc*`。

也就是说，一旦该能力被采纳，当前 `program_model.adoc` 中“8 个矩阵寄存器”的摘要需要扩展为包含 scale 寄存器的版本。

==== 初始化、失效与异常

为了避免“scale 未加载但结果悄悄错误”的情况，建议把 scale 寄存器的有效性作为架构语义的一部分：

* 上电复位后，所有 `sa*` / `sb*` 处于 **invalid** 状态。
* `minit` 执行后，所有 `tr*`、`acc*`、`sa*`、`sb*` 都重新进入可丢弃的初始状态；其中 `sa*` / `sb*` 也变为 **invalid**。
* 只有对应的 scale load 指令成功写入后，目标 `sa*` / `sb*` 才变为 **valid**。
* 若某条 scaled matmul 需要读取的 `sa*` 或 `sb*` 仍为 invalid，建议抛出 **illegal instruction exception**。

这里的 invalid/valid 位不要求提供独立的可读 CSR；实现可以把它们视为与 scale 寄存器绑定的隐含架构状态。

==== 与现有指令的关系

* `mzero` 只作用于矩阵寄存器，不修改 `sa*` / `sb*`。
* `minit` 应扩展为同时使 scale 状态失效。
* 当前 whole-register load/store 仅覆盖 tile/acc 的语义，尚未定义 scale 寄存器的整体保存/恢复指令。

第一阶段建议先不设计独立的 scale save/restore 指令，而是要求软件在上下文恢复后重新加载 scale 数据。待 block scaling 路线稳定后，再决定是否需要 whole-scale load/store。
