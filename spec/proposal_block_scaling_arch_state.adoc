=== 基于 Scale 寄存器的架构状态提案

==== 设计动机

NVIDIA 和 AMD 的公开 ISA 都更接近“每条 matmul 显式接收 scale 输入”的模式。但对本仓库的 32-bit 指令编码约束而言，若同时保留：

* A/B 操作数寄存器编号
* 输出寄存器编号
* A/B 类型选择
* 混合类型支持
* scale 类型与 block scaling 模式

则单条矩阵乘法指令的编码压力会迅速失控。因此，这里提出一个 **RISC-V 化的 scale 寄存器方案**：把 scale 作为可见架构状态，而不是每条指令的显式附加操作数。

==== 新增架构状态

在现有 `tr0-tr3`、`acc0-acc3` 之外，新增 8 个 scale 寄存器：

[cols="^2,^2,^7",options="header"]
|===
| Category | Name | Description
| A-side scale | sa0-sa3 | A 操作数对应的 scale 寄存器组
| B-side scale | sb0-sb3 | B 操作数对应的 scale 寄存器组
|===

这里的 `sa*` / `sb*` 只是逻辑命名。它们是否占用统一的矩阵寄存器编号空间，还是在编码上使用独立寄存器类，留待后续编码提案收敛时再冻结。

语义上的关联关系固定为：

* `sa[i]` 与 `tr[i]` 配对，表示 A 操作数的 scale。
* `sb[i]` 与 `tr[i]` 配对，表示 B 操作数的 scale。

这样的固定配对牺牲了一部分灵活性，但避免了在 matmul 编码中额外加入两个 scale 寄存器字段。

==== Scale 寄存器容量

对某一类 block scaling 格式，定义：

* `block_size(fmt)`：该格式的块大小，例如 MX 路线为 32。
* `scale_bits(fmt)`：scale 在寄存器中的存储位宽，例如 `UE8M0` 为 8。

则单个 scale 寄存器每行位宽为：

----
SRLEN(fmt) = (TRLEN / block_size(fmt)) * scale_bits(fmt)
----

单个 scale 寄存器总位宽为：

----
SLEN(fmt) = ROWNUM * SRLEN(fmt)
----

对第一阶段建议范围 `UE8M0 + block_size=32`：

----
SRLEN = TRLEN / 4
SLEN  = TLEN / 4
----

这意味着 scale 寄存器的物理容量明显小于 tile 寄存器，适合实现为独立寄存器文件，或实现为 tile 文件旁边的缩比寄存器区。

==== 逻辑形状

为了和当前 `C = A x B^T` 的 tile 存储方式对齐，scale 寄存器的**逻辑形状**应和操作数在 tile 寄存器中的方向一致，而不是和未转置的原始矩阵概念强行对齐：

* `sa[i]` 的活动形状：`mtilem x ceil(mtilek / block_size)`
* `sb[i]` 的活动形状：`mtilen x ceil(mtilek / block_size)`

其中：

* `sa[i]` 的行对应 A tile 的 `M` 维。
* `sb[i]` 的行对应 B tile 在寄存器中的 `N` 维，因为当前右操作数以 `B^T` 形式参与计算。

从源矩阵的数学视角看，B-side scale 仍可理解为 `(mtilek / block_size) x mtilen`；这里采用 `mtilen x ceil(mtilek / block_size)` 只是为了和当前 `B^T` 寄存器布局保持一致，便于描述寄存器内活动形状和逐行加载约定。

==== 上下文与 MS 状态

如果实现 block scaling 能力，则 scale 寄存器属于 **matrix context** 的一部分：

* 对 `sa*` / `sb*` 的写入会使 `MS` 从 Initial/Clean 进入 Dirty。
* 执行使用 scale 的 matmul 会读取 scale 寄存器，因此 scale 寄存器必须参与上下文切换语义。
* OS 或运行时在保存/恢复 matrix context 时，不能只考虑 `tr*` 和 `acc*`。

也就是说，一旦该能力被采纳，当前 `program_model.adoc` 中“8 个矩阵寄存器”的摘要需要扩展为包含 scale 寄存器的版本。

==== 初始化、失效与异常

为了避免“scale 未加载但结果悄悄错误”的情况，建议把 scale 寄存器的有效性作为架构语义的一部分：

* 上电复位后，所有 `sa*` / `sb*` 处于 **invalid** 状态。
* `minit` 执行后，所有 `tr*`、`acc*`、`sa*`、`sb*` 都重新进入可丢弃的初始状态；其中 `sa*` / `sb*` 也变为 **invalid**。
* 只有对应的 scale load 指令成功写入后，目标 `sa*` / `sb*` 才变为 **valid**。
* 若某条 scaled matmul 需要读取的 `sa*` 或 `sb*` 仍为 invalid，建议抛出 **illegal instruction exception**。

这里的 invalid/valid 位不要求提供独立的可读 CSR；实现可以把它们视为与 scale 寄存器绑定的隐含架构状态。

==== 与现有指令的关系

* `mzero` 只作用于矩阵寄存器，不修改 `sa*` / `sb*`。
* `minit` 应扩展为同时使 scale 状态失效。
* 当前 whole-register load/store 仅覆盖 tile/acc 的语义，尚未定义 scale 寄存器的整体保存/恢复指令。

第一阶段建议先不设计独立的 scale save/restore 指令，而是要求软件在上下文恢复后重新加载 scale 数据。待 block scaling 路线稳定后，再决定是否需要 whole-scale load/store。

重新加载 scale 的约定不等于对异步抢占的透明恢复。写 `MS=Off` 或 Initial 不清除寄存器。
向另一任务开放矩阵状态前，平台必须排空或隔离旧任务的在途工作，使旧 scale 失效，
并恢复新任务自己的 `tr*` / `acc*` 或清除前任数据。若不能透明恢复，被抢占任务必须
能在使用已丢失的状态前识别这一情况。不能满足这些条件时，不得承诺任务间 AME 隔离。

==== 第一阶段实验编码

为了在完整编码表收敛前打通软件、golden model、模拟器和 RTL，本提案先冻结一个
可验证的实验子集。该子集只覆盖 MX32/E8M0，不覆盖 NVFP4、UE4M3、FP6 或
scale save/restore。

scale 寄存器与 tile 寄存器的编号绑定：

[cols="^1,^1,^1"]
|===
| 字段值 | A scale | B scale
| 000-011 | `sa0`-`sa3` | `sb0`-`sb3`
|===

`mlascale` / `mlbscale` 使用 load/store 格式，`func3=001`、`l/s=0`、
`func4[1:0]=11`。该组合在普通 A/B/C load/store 中是 reserved。

[cols="^2,^2,^8"]
|===
| `func4` | `kind` | 指令
| 0011 | `11` | `mlascale`
| 1011 | `11` | `mlbscale`
| 其他 `kind=11` | `11` | reserved
|===

字段语义：

* `md[1:0]` 选择 `sa0`-`sa3` 或 `sb0`-`sb3`，`md[2]` 必须为 0。
* `rs1` 是 E8M0 scale 数组基地址。
* `rs2` 是相邻 scale 行的字节 stride。
* scale 数据按 `[row][scale_block]` row-major 排列，每个元素 8 bit。
* 行数由当前 `mtilem`（`mlascale`）或 `mtilen`（`mlbscale`）决定。
* 每行 scale block 数由 `ceil(mtilek / 32)` 决定。
* load 完成后，目标 scale 寄存器进入 valid 状态。
* 地址不对齐、目标 index 非 0-3、`mtilek=0` 或 `rs2` 不足以覆盖一行时，
  抛出 illegal instruction exception。

一次成功的 scale load 同时记录其活动形状
`rows = (mlascale ? mtilem : mtilen)` 和
`blocks = ceil(mtilek / 32)`。scale 寄存器保持 valid，并可在后续 scaled
`mmacc` 中重复使用，直到同一寄存器被一次新的 scale load 覆盖或 `minit`
使其 invalid。重复使用不会消耗或自动切换 scale 寄存器。

新 load 完整覆盖目标寄存器的活动形状；部分形状不会与旧内容合并。
scaled `mmacc` 要求的 `rows`/`blocks` 必须被该寄存器最近一次成功 load
所记录的活动形状覆盖。否则不得读取旧或未初始化字节，必须抛出 illegal
instruction exception。

`mmacc` 的编码不增加操作数。是否使用 scale 由 `mcfg` 的 block-scaled
table 和源操作数类型共同决定。CPU 在内部 AMU payload 的 reserved 区域携带
`scale_mode`：

[cols="^1,^8"]
|===
| `scale_mode` (`MteComputeType`) | 含义
| 0111 | MXFP8 E4M3, block size 32
| 1000 | MXFP8 E5M2, block size 32
| 1010 | MXFP4 E2M1, block size 32
|===

该字段不改变 32-bit software instruction encoding；它是 CPU 生成的 AMU
内部元数据，用于避免把 scaled 与 unscaled FP8 混淆。其 4-bit 数值与
`MteComputeType` 一致。普通 unscaled 操作不携带 scale 元数据。

CPU 产生的 150-bit AMU 负载使用现有 spare 位，不改变软件 ABI：

* `AmuLsuIO[130:127]`：上述 4-bit `MteComputeType`；
* `AmuLsuIO[126]`：`isScale`；
* `AmuMmaIO[56:53]`：上述 4-bit `MteComputeType`；
* 其余 spare 位必须为 0。

物理 scale bank 编号、owner 和 generation 属于实现内部状态，不由软件
payload 提供。实现不得把独立 bank toggle 顺序当作软件可见寄存器所有权。

block-scaled `mmacc` 必须同时满足：

* `mcfg(ms1)`、`mcfg(ms2)` 和 `mcfg(md)` 的类型组合合法；
* `sa[ms1[1:0]]` 与 `sb[ms2[1:0]]` 都 valid；
* 两者的活动形状覆盖当前 `mtilem`/`mtilen`/`mtilek`。

任一条不满足时，不执行部分运算，抛出 illegal instruction exception。
