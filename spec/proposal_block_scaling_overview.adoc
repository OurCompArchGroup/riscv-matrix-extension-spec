== 概述与范围

=== 问题

当前主 spec 仅支持 `mmacc.w.b`（int8 x int8 -> int32）。如果未来要支持 FP8、FP6、FP4 等低精度矩阵乘法，仅靠量化数据本身通常不足以覆盖推理所需动态范围，必须配合 block scaling。

核心计算语义可以写为：

----
D[i][j] += (A[i][k] * scale_A[i][k / B]) * (B[k][j] * scale_B[k / B][j])
----

其中 `B` 为 block 大小。对 MX 类格式，`B` 通常为 32；对 NVIDIA 私有 NVFP4 类格式，`B` 常见为 16。

=== 业界共识

结合 NVIDIA 和 AMD 的官方公开资料，block scaling 至少有以下共识：

* `scale` 与量化数据分离，不打包在同一个矩阵元素里。
* `scale` 由矩阵乘法指令消费，而不是写回到通用 CSR 后再隐式广播。
* block 大小与数据格式绑定，不由软件在运行时任意配置。
* 混合 A/B 低精度类型是现实需求，例如 `e4m3 x e5m2`。

=== 本提案的拆分目标

本提案不再把所有问题揉在一份文档里，而是拆成三类核心问题和一类业界基线对照：

* **概述与范围**：回答为什么需要 block scaling，以及第一阶段到底收敛到哪里。
* **架构状态**：回答如果采用 scale 寄存器方案，需要新增哪些架构状态、上下文语义和异常语义。
* **执行与编码**：回答矩阵乘法编码空间不够时，应如何收敛执行模型与编码方向。
* **业界基线**：保留 NVIDIA/AMD 的共识方案，作为备选设计与比较基线。

=== 第一阶段建议收敛范围

为了避免 proposal 发散，建议第一阶段只把下面几件事作为主方案：

* 采用 **scale 寄存器方案** 作为本仓库的首选架构方向。
* 只冻结 **MX 路线**，即 `UE8M0` scale 与 `block size = 32`。
* 只冻结“存在 block scaling 的执行模型”，不在本阶段把所有 `s_type` 编码表一次写死。
* `NVFP4 + UE4M3`、`FP6`、以及更复杂的混合格式先保留在扩展讨论中。

这样做的目的不是否定 NVIDIA/AMD 的显式 scale 输入路径，而是承认当前 32-bit 指令编码空间有限，本仓库需要一个更适合自身约束的第一阶段方案。

=== 发现机制约束

本提案默认沿用当前 spec 的发现机制方向：

* 不新增 `misa` 单比特能力位。
* 扩展名通过 `riscv,isa-extensions` 报告。
* 具体矩阵能力通过 device tree capability string 报告。

也就是说，block scaling 的存在应通过设备树能力模型表达，而不是回退到新的 `misa` 位设计。
