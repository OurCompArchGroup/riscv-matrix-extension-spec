== Zmasync: Optional Asynchronous Store Synchronization Extension

=== Overview

The motivation of Zmasync is to allow matrix operations to be pipelined with vector operations, which is required by state-of-the-art kernel libraries such as Flash Attention 3 and DeepGEMM, where matrix multiplication results need post-processing (e.g., precision promotion) that can overlap with the next matrix operation.

The Zmasync extension enables asynchronous execution of matrix operations within a single core. The term "asynchronous" in this context specifically refers to asynchrony between different functional units within a single core (not multi-core or multi-hart asynchrony). This allows matrix operations to overlap with other operations, such as vector or scalar computations, within the same hart.

When the Zmasync extension is implemented together with the AME (Attached Matrix Extension) or its simplified variant, the behavior of matrix load/store/`mmacc`/`mzero` instructions changes: these instructions become non-blocking without any modification to their instruction encoding, and are committed immediately from the pipeline without waiting for completion. However, store results are not guaranteed to be visible to subsequent vector or scalar loads immediately. To ensure the visibility of the store operations, the Zmasync extension introduces a new set of synchronization instructions.

NOTE: The `mcsr` register and its sub-registers (e.g., `mfflags`, `msat`) reflect the results of asynchronous matrix operations only after a corresponding `macquire` instruction is executed. Reading `mcsr` or its sub-registers before `macquire` following an asynchronous matrix operation yields undefined behavior.

==== Sync Register Count CSR, msync

The read-only `msync` CSR (address 0xCC7) reports the number of implemented sync registers. Legal sync register indices are in the range `0` to `msync - 1`. Encodings that specify `sync >= msync` are reserved and raise an illegal instruction exception. In this specification, the implementation provides exactly 16 sync registers, so sync indices `16` to `31` are reserved.

=== Instruction Format

The Zmasync instruction category uses `func3 = 100`. Bits `inst[27:26]` are reserved and shall be `00`. The `func4` field distinguishes different synchronization operations. The `sync` field (`inst[24:20]`) specifies the sync register index when the instruction operates on a sync register. The `ctrl` field (`inst[25]`) is set to 0. For `msyncregreset` and `mrelease`, the `rs1` field is set to zero. For `macquire`, the `rs1` field specifies the scalar register containing the threshold value. For `mfence`, both `sync` and `rs1` are reserved and shall be zero.

=== Instructions

==== Reset, Release and Acquire

```
msyncregreset tok0           # Reset sync register tok0 to 0.

mrelease      tok0           # Increment tok0 by 1; waits for store visibility.

macquire      tok0, t0       # Block until tok0 >= t0; ensures store visibility
                             # to other units.

mfence                       # Ensure non-matrix memory data is visible to the
                             # matrix engine.
```

`msyncregreset` resets the specified sync register to zero, clearing any previously accumulated release count.

`mrelease` increments the sync register by one. It does not commit until all in-flight matrix store instructions from the current thread have been made visible to subsequent vector and scalar loads, ensuring that memory written by those stores is observable before the release count advances.

`macquire` blocks until the sync register value is greater than or equal to the threshold supplied in an integer register. In a pipelined GEMM schedule, this acts as the completion check for the current matrix-engine work item. Once `macquire` succeeds, the software can treat the current matrix result as finished and visible to the non-matrix units. At that point, the matrix engine may continue with the next block, while vector or scalar code consumes the completed result for post-processing such as precision promotion.

`mfence` is the reverse-direction companion to `macquire`. It is a single-hart, intra-core visibility barrier that guarantees memory data produced outside the matrix engine is visible to subsequent matrix-engine memory operations. `mfence` does not use a sync register and does not define any cross-hart or system-wide ordering semantics.

==== Usage Example: GEMM in AME with Zmasync

In a GEMM pipeline, asynchronous matrix operations allow the next GEMM to execute while the previous result is being post-processed by scalar or vector execution.

```
void async_matmul(c);  // output matrix c

void promotion(c);

void vector_init_matmul_inputs(a, b);

void gemm_kernel() {
    ...

    num_iterations = 10;

    tok0 = msyncregreset();           // tok0 = 0

    vector_init_matmul_inputs(a, b);  // vector/scalar units initialize
                                      // the raw input arrays
    mfence();                         // make non-matrix-produced inputs
                                      // visible to the matrix engine

    async_matmul(c[0]);               // launch the first matrix multiply
    mrelease(tok0);                   // once async_matmul completes, tok0 += 1

    for (i = 1; i < num_iterations; i++) {

        async_matmul(c[i]);
        mrelease(tok0);

        macquire(tok0, i);            // wait until the previous matrix result is complete
        promotion(c[i - 1]);          // once the previous matrix multiply
                                      // completes, promote its result.
    }

    macquire(tok0, num_iterations);   // wait until the final matrix result is complete
    promotion(c[num_iterations - 1]); // promote the final completed result
    ...
}
```

Above pseudocode gives an example of how to use Zmasync to implement GEMM in AME.
The `async_matmul` function is a non-blocking matrix multiplication function
implemented with asynchronous matrix store instructions,
which retires from the pipeline without waiting for the completion.
After asynchronous matrix store instructions in `async_matmul` function is finally completed,
`mrelease` will increment the sync register by one.
`macquire` blocks until the sync register value reaches or exceeds the given threshold (i.e., `sync >= threshold`). In this example, it serves as the check that the previously launched matrix block has finished. Once it returns, that completed result can be consumed safely by the vector pipeline for precision promotion, while the matrix engine is free to continue processing the next block. A final `macquire` / `promotion` pair drains the tail of the pipeline after the last matrix block has been launched. Note that an exact match is not required — if the sync register has advanced beyond the threshold, `macquire` still proceeds immediately. Without Zmasync, all operations would execute sequentially on the core, with no overlap between GEMM and promotion.
`vector_init_matmul_inputs` represents scalar or vector code that initializes the raw operand arrays later consumed by matrix load or matrix multiply instructions.
`mfence` is used before dispatching asynchronous matrix work when the matrix engine must observe memory data that was produced by scalar or vector execution earlier in the same hart.
